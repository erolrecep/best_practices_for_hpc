Unlocking the full potential of advanced computing requires moving beyond the mindset of simply scaling up local code. Simply put: an HPC cluster is not just a bigger laptop; it is a highly orchestrated ecosystem. Navigating these powerful resources requires adaptation. Everyone needs help scaling up, and as HPC experts at the Center for Research Computing (CRC), we consider ourselves your research partners.  1. Access and The Shared Resource Mindset
The foundation of efficient HPC usage begins with how you access the system. RANGE provides two primary entry points: traditional SSH for terminal-based workflows and OpenOnDemand (OOD) for web-based, interactive applications like Jupyter Notebooks and MATLAB.
A critical rule of thumb on any shared cluster is understanding the difference between login nodes and compute nodes. Login nodes are strictly for navigating the file system, editing scripts, and submitting jobs to the Slurm scheduler. They are not designed for remote software execution, heavy compiling, or running resource-intensive IDE plugins (such as VSCode server, Codex, or Copilot). Running compute-heavy tasks on login nodes degrades the experience for everyone on the cluster. Always request an interactive session (via salloc or OOD) for debugging or exploratory data analysis, and rely on batch jobs (sbatch) for your heavy lifting and automated runs.
 2. High-Performance Data Transfer and Storage Hygiene
Data transfer is often the first major hurdle in large-scale computing. Moving a few megabytes from your laptop is trivial, but migrating terabytes of data between external institutions and RANGE requires the right tools.
For small to medium synchronization tasks, rsync is a reliable choice. However, for multi-terabyte datasets, Globus is absolutely essential. Globus manages background transfers, handles network interruptions gracefully, and ensures data integrity without tying up your active terminal session. If you are unsure which protocol suits your data constraints, consult with the CRC team.
Once your data is on RANGE, storage hygiene becomes paramount. RANGE utilizes a high-performance storage system designed specifically for rapid I/O during active compute jobs. This "scratch" space is built for speed, not permanence. It is neither a personal data vault nor a long-term lab archive. You do not need to write every intermediate variable to disk; keep only the essential outputs. Frequently audit your storage footprint, back up crucial results to your long-term storage solutions, and clean up intermediate files once your job successfully completes.
 3. Structuring Reproducible Scientific Workflows
Scientific computing is a marathon. Over the lifecycle of a project, you will constantly add, modify, and remove components. Ensuring reproducibility and maintainability across all these stages is non-negotiable.
We recommend testing your code on your local PC using a scaled-down dataset first, ensuring that the exact same software environment is mirrored on the HPC cluster. To achieve this, abandon hidden local dependencies and embrace containerization. By packaging your workflows using Apptainer (formerly Singularity), you guarantee that your code will execute seamlessly regardless of the underlying host environment. Test locally, then deploy the identical container on RANGE.
Additionally, automate your build and execution steps using management tools like Makefile or CMake. Maintain a dedicated folder structure that pairs your submitted Slurm job scripts with their respective output logs. This historical record of job submissions and their behaviors is invaluable for debugging and profiling later runs.
 4. Mastering Resource Allocation: CPU and Memory
Resource allocation is the heart of HPC. Because RANGE is a shared, resource-limited environment, your code should strictly utilize what you request. Blind overallocation inflates your queue times and prevents other researchers from running their jobs.
The Memory Trap: A common anti-pattern is the "128GB vs. 16GB" trap. A user might request 128 GB of RAM "just to be safe," even though their data processing script never exceeds 16 GB in practice. Consequently, the Slurm scheduler leaves the job pending for days waiting for a massive memory block to open up. Profile your code locally, start small, and use tools like seff <jobid> after your initial runs to review historical resource consumption and refine your future requests.
The Sequential Trap: Another frequent pitfall is the "One-by-One" trap—submitting a single script that runs 1,000 independent simulations sequentially. This wastes massive amounts of time and leaves allocated multi-core nodes sitting idle. Instead, embrace parallel computing by utilizing Slurm Job Arrays. Job arrays allow you to submit hundreds of concurrent tasks under a single job ID, radically optimizing your runtime and cluster throughput.
 5. Hardware Acceleration: Optimizing GPU Jobs
As a veteran HPC engineer specializing in hardware-accelerated computing, I see GPU underutilization as one of the most critical issues on modern clusters. RANGE features cutting-edge NVIDIA GPUs, which are incredibly powerful but highly sought after.
A frequent error is requesting an entire multi-GPU node (e.g., --gres=gpu:4) for a script that is hardcoded to use a single device (e.g., cuda:0). In this scenario, one GPU does the work while three highly expensive accelerators sit entirely idle, effectively locked away from the rest of the university. If you request multiple GPUs, your code must be explicitly written to leverage them (for example, using frameworks like PyTorch's DistributedDataParallel). Always verify your GPU utilization in real-time during an interactive session using tools like nvtop or nvidia-smi to ensure your code is truly saturating the requested hardware.
